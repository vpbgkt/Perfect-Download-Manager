# Requirements Document

## Introduction

This feature extends the existing PDM license-key system in three directions, without changing
the architecture it already runs on:

1. **Customer information on license keys.** Today a License_Record carries only a free-text
   `owner` label, so support staff cannot reliably identify who holds a key, find every key
   belonging to one person, or reach that person. This feature adds a defined set of optional
   Customer_Fields (email, contact number, country, contact name, company, notes) stored as
   additive attributes on the same `pdm-licenses` item, prompted at creation time, editable
   afterwards, and searchable. Email is deliberately non-unique: one person may hold many keys.

2. **Custom key prefixes.** License_Keys are currently minted as
   `PDM-XXXX-XXXX-XXXX-XXXX` (four groups of four uppercase hex characters, 64 bits of
   randomness) by two code paths that must stay in agreement:
   `admin-portal/lib/licenses/keygen.ts` and `backend/licensing/admin/create-license.mjs`.
   This feature lets an Admin_User attach a meaningful Custom_Key_Prefix — for a campaign,
   seller, or organization — producing keys such as `PDM-NEW-YEAR-…` or
   `PDM-VISHAL-ENTERPRISE-…`, while the secret tail is still generated by a cryptographically
   secure generator with no dependence on the prefix.

3. **Hardened key secrecy and brute-force resistance.** The secret component's entropy is
   raised for newly minted keys, the generator's independence from all predictable inputs is
   made explicit and testable, and the `/activate` and `/validate` endpoints gain per-source-IP
   attempt limiting. Today only `/trial` is rate limited
   (`backend/licensing/src/lib/rateLimit.mjs`); `/activate` and `/validate` rely solely on the
   API Gateway stage throttle (10 requests/second, burst 20) shared across all callers.

The feature is strictly additive with respect to existing data and clients. Every existing
License_Key remains valid, every existing item keeps its attributes, existing request and
response shapes keep working, and the shipped desktop client needs no change: the licensing
backend's shared input validator already accepts any key matching
`^[A-Za-z0-9\-]{8,128}$` (`backend/licensing/src/lib/http.mjs`) and the .NET client
(`src/PDM.Licensing/LicenseService.cs`) forwards the entered key without imposing a format.

Scope covered here: the Admin_Reseller_Portal (`admin-portal`), the licensing Lambdas and
CloudFormation template (`backend/licensing`), the admin CLI minter, tests, and deployment to
the existing AWS environment in `ap-south-1`. Out of scope: the ECDSA token signing scheme, the
client-embedded public key, and the trial-anchor flow.

## Glossary

- **Admin_Reseller_Portal**: The authenticated web application in `admin-portal` comprising the
  Portal_Frontend and the Portal_Backend.
- **Portal_Frontend**: The browser dashboard of the Admin_Reseller_Portal.
- **Portal_Backend**: The server-side API of the Admin_Reseller_Portal (the `app/api/*` route
  handlers and the `lib/*` modules they call).
- **Licensing_Backend**: The pre-existing serverless licensing service in region `ap-south-1`:
  the `pdm-licenses` DynamoDB table, the activate/validate/deactivate/trial Lambda functions,
  and the HTTP API in front of them.
- **Licenses_Table**: The existing DynamoDB table `pdm-licenses`, partition key `licenseKey`,
  holding License_Record items, trial-anchor items, and rate-limit counter items.
- **License_Record**: One non-trial, non-counter item in the Licenses_Table, holding the
  existing attributes `licenseKey`, `status`, `plan`, `owner`, `features`, `maxActivations`,
  `maxConn`, `maxParallel`, `expiresAt`, `activations`, `createdAt`, and the additive attribute
  `resellerAccountId`.
- **License_Key**: The value of a License_Record's `licenseKey` attribute, used by a customer to
  activate the desktop application.
- **Legacy_License_Key**: A License_Key in the format `PDM-XXXX-XXXX-XXXX-XXXX`, where each
  `XXXX` group is four uppercase hexadecimal characters, as minted before this feature.
- **Key_Alphabet**: The 32-symbol set used for a Key_Secret_Component: the digits `0`–`9` and
  the uppercase letters `A`–`Z` excluding `I`, `L`, `O`, and `U`.
- **Key_Secret_Component**: The randomly generated tail of a License_Key, written as
  hyphen-separated groups of four Key_Alphabet symbols.
- **Custom_Key_Prefix**: An optional, human-meaningful identifier inserted between the literal
  segment `PDM` and the Key_Secret_Component of a generated License_Key, for example
  `NEW-YEAR` or `VISHAL-ENTERPRISE`.
- **Key_Generator**: The component that produces a License_Key, implemented in
  `admin-portal/lib/licenses/keygen.ts` and mirrored by
  `backend/licensing/admin/create-license.mjs`.
- **Customer_Field**: One of the additive License_Record attributes `customerEmail`,
  `customerName`, `customerPhone`, `customerCountry`, `customerCompany`, and `customerNotes`.
- **Customer_Profile**: The set of Customer_Field values stored on one License_Record.
- **Email_Format**: A string of 1 to 254 characters containing exactly one `@`, with a local
  part of 1 to 64 characters before the `@`, a domain of at least 3 characters after the `@`
  that contains at least one `.` and neither begins nor ends with `.`, and no whitespace
  character anywhere.
- **Country_Code**: A two-character ISO 3166-1 alpha-2 country code composed of uppercase
  letters `A`–`Z`.
- **Phone_Format**: A string of 7 to 20 characters composed of digits, spaces, hyphens,
  parentheses, and at most one `+` that appears only as the first character, containing at
  least 7 digits.
- **Portal_User**: An authenticated principal of the Admin_Reseller_Portal holding exactly one
  of the roles `super_admin`, `admin`, or `reseller`.
- **Admin_User**: A Portal_User holding the `super_admin` or `admin` role.
- **Reseller_User**: A Portal_User holding the `reseller` role.
- **Reseller_Account**: The organization record a Reseller_User belongs to, referenced by a
  License_Record's `resellerAccountId` attribute.
- **Reseller_API**: The subset of Portal_Backend endpoints authenticated by an Api_Key on behalf
  of a Reseller_Account.
- **Permission**: A named capability gating a Portal_Backend operation, for example
  `license:create`, `license:read`, `license:update`.
- **Viewable_Record**: A License_Record that the requesting Portal_User is authorized to read
  under the existing ownership rules: any non-trial record for an Admin_User, and only records
  whose `resellerAccountId` equals the caller's Reseller_Account for a Reseller_User.
- **Mutation**: Any Portal_Backend operation that creates, updates, or removes persistent state.
- **Audit_Entry**: One immutable record appended to the portal's append-only audit log,
  capturing actor identity, actor role, action, target identifier, source IP, timestamp, and
  the names of changed attributes.
- **Activation_Endpoint**: The Licensing_Backend route `POST /activate`, handled by
  `backend/licensing/src/activate.mjs`.
- **Validation_Endpoint**: The Licensing_Backend route `POST /validate`, handled by
  `backend/licensing/src/validate.mjs`.
- **Attempt_Counter**: A counter item in the Licenses_Table recording the number of requests
  observed for one endpoint and one source IP within one time window, carrying the numeric
  epoch-second time-to-live attribute `ttl`.
- **Attempt_Window**: The fixed time span over which one Attempt_Counter accumulates.
- **License_Token**: The ECDSA-signed token the Licensing_Backend returns from the
  Activation_Endpoint and the Validation_Endpoint.
- **Deployment_Process**: The scripted sequence that builds the Admin_Reseller_Portal, applies
  the `backend/licensing` CloudFormation template, publishes the Lambda package, and verifies
  the deployed environment.

## Requirements

### Requirement 1: Capture Customer Information at License Creation

**User Story:** As an Admin_User or Reseller_User, I want to record a customer's contact details
while I mint their key, so that support can later identify the key's owner without guesswork.

#### Acceptance Criteria

1. WHEN a Portal_User with the `license:create` Permission opens the create-license form, THE
   Portal_Frontend SHALL display one input control for each of the six Customer_Fields together
   with text stating that every Customer_Field is optional and recommended.
2. WHEN a Portal_User with the `license:create` Permission submits a create-license request
   carrying one or more Customer_Field values that satisfy the validation rules of Requirement 4,
   THE Portal_Backend SHALL store each submitted value, in the normalized form required by
   Requirement 4, as the correspondingly named attribute of the created License_Record and SHALL
   omit from the stored item every Customer_Field attribute whose value is absent.
3. WHEN a Portal_User submits a create-license request in which every Customer_Field is absent,
   meaning omitted from the request, null, or a string containing only whitespace characters, THE
   Portal_Backend SHALL create the License_Record and SHALL omit every Customer_Field attribute
   from the stored item.
4. THE Portal_Backend SHALL store Customer_Fields as attributes of the same License_Record item
   in the Licenses_Table and SHALL hold no second copy of any Customer_Field value in another
   data store.
5. WHERE a submitted `customerEmail` value equals the `customerEmail` value of one or more
   existing License_Records, THE Portal_Backend SHALL create the License_Record without
   rejecting the request and SHALL keep every License_Record carrying that `customerEmail` value
   retrievable as a Viewable_Record.
6. WHEN a Reseller_User submits a create-license request carrying Customer_Field values, THE
   Portal_Backend SHALL store those values on the created License_Record and SHALL set that
   record's `resellerAccountId` to the caller's Reseller_Account.
7. WHEN a Reseller_API create-license request carries Customer_Field values, THE Portal_Backend
   SHALL apply the validation and normalization rules of Requirement 4 and the storage rules of
   criteria 2 through 4 of this requirement, unchanged from a Portal_Frontend create-license
   request.
8. WHEN a License_Record is created with at least one Customer_Field value, THE Portal_Backend
   SHALL append an Audit_Entry recording the actor identity, the actor role, the License_Key,
   the source IP, an ISO 8601 UTC timestamp, and the names of the Customer_Fields that were set,
   and SHALL exclude every Customer_Field value from that Audit_Entry.
9. IF a create-license request carrying one or more Customer_Field values is submitted by a
   requester that does not hold the `license:create` Permission, THEN THE Portal_Backend SHALL
   reject the request with a not-authorized response, SHALL write no License_Record, and SHALL
   store no Customer_Field value.
10. IF the Licenses_Table write of a create-license request fails, THEN THE Portal_Backend SHALL
    return an error response indicating that the License_Record was not created and SHALL leave
    every item in the Licenses_Table unchanged.

### Requirement 2: Add and Update Customer Information After Creation

**User Story:** As a support Admin_User, I want to fill in or correct a key's customer details
later, so that a key created in a hurry can still be traced to its owner.

#### Acceptance Criteria

1. WHEN a Portal_User with the `license:update` Permission submits one or more of the six
   Customer_Fields for a Viewable_Record with values that satisfy the validation rules of
   Requirement 4, THE Portal_Backend SHALL store each submitted value, in the normalized form
   required by Requirement 4, as the correspondingly named attribute of that License_Record and
   SHALL leave every attribute that was not submitted, including `licenseKey`, unchanged.
2. WHEN a Portal_User with the `license:update` Permission submits a Customer_Field of a
   Viewable_Record with a value that is null, an empty string, or a string containing only
   whitespace characters, THE Portal_Backend SHALL remove that Customer_Field attribute from the
   License_Record, and SHALL leave the License_Record unchanged where that attribute is already
   absent.
3. WHEN a Portal_User with the `license:read` Permission opens a Viewable_Record in the
   Portal_Frontend, THE Portal_Frontend SHALL display one editable control for each of the six
   Customer_Fields, pre-filled with the stored value for each Customer_Field that has one and
   empty for each Customer_Field that has none.
4. WHEN a Portal_User submits the same Customer_Field values for the same License_Record a
   second time with no intervening change, THE Portal_Backend SHALL leave the stored
   Customer_Profile equal to the value it held after the first submission and SHALL leave every
   other attribute of that License_Record unchanged.
5. IF a Customer_Field update names a License_Key that is not a Viewable_Record for the
   requester, THEN THE Portal_Backend SHALL return a not-found response and SHALL leave every
   item in the Licenses_Table unchanged.
6. IF a Customer_Field update names a License_Key beginning with `TRIAL#` or `RL#`, THEN THE
   Portal_Backend SHALL return a not-found response and SHALL leave every item in the
   Licenses_Table unchanged.
7. WHEN one or more Customer_Fields of a License_Record are changed, THE Portal_Backend SHALL
   append an Audit_Entry recording the actor identity, the actor role, the License_Key, the
   source IP, an ISO 8601 UTC timestamp, and the names of the changed Customer_Fields, and SHALL
   exclude every Customer_Field value from that Audit_Entry.
8. IF a Customer_Field update is submitted by a requester that does not hold the
   `license:update` Permission, THEN THE Portal_Backend SHALL reject the request with a
   not-authorized response and SHALL leave every item in the Licenses_Table unchanged.
9. IF the Licenses_Table write of a Customer_Field update fails, THEN THE Portal_Backend SHALL
   return an error response indicating that the License_Record was not updated and SHALL leave
   every item in the Licenses_Table unchanged.
10. WHERE a submitted `customerEmail` value equals the `customerEmail` value of one or more other
    existing License_Records, THE Portal_Backend SHALL apply the update without rejecting the
    request and SHALL keep every License_Record carrying that `customerEmail` value retrievable
    as a Viewable_Record.

### Requirement 3: Find Licenses by Customer Information

**User Story:** As a support Admin_User, I want to look up every key belonging to a customer by
their email, name, or company, so that I can answer "which keys do I own?" in one search.

#### Acceptance Criteria

1. WHEN a Portal_User with the `license:read` Permission opens a Viewable_Record, THE
   Portal_Backend SHALL return every Customer_Field stored on that License_Record and SHALL omit
   from the response every Customer_Field that is absent from that License_Record.
2. WHEN a Portal_User with the `license:read` Permission submits a license search term of 1 to
   128 characters after leading and trailing whitespace is removed, THE Portal_Backend SHALL
   return every Viewable_Record in which that trimmed term occurs as a substring of `licenseKey`,
   `owner`, `customerEmail`, `customerName`, `customerCompany`, or `customerPhone` when the term
   and the attribute value are both compared converted to lowercase, and SHALL return an empty
   result set with no continuation token and no error where no Viewable_Record matches.
3. WHEN a Portal_User submits a license search term that, trimmed and converted to lowercase,
   equals a stored `customerEmail` value, THE Portal_Backend SHALL return every Viewable_Record
   carrying that `customerEmail` value across the pages retrieved with successive continuation
   tokens.
4. WHEN a license search matches more Viewable_Records than one page holds, THE Portal_Backend
   SHALL return one page holding at most the page size supplied by the request, defaulting to 50
   Viewable_Records where the request supplies no page size and capped at 100 Viewable_Records,
   together with a continuation token that the requester passes back unchanged to retrieve the
   next page, SHALL omit the continuation token from the final page, and SHALL yield each
   matching Viewable_Record exactly once across the pages retrieved with successive continuation
   tokens.
5. WHEN a Reseller_User submits a license search term, including through the Reseller_API, THE
   Portal_Backend SHALL return only License_Records whose `resellerAccountId` equals the caller's
   Reseller_Account and SHALL exclude every other License_Record from the result set and from the
   result count.
6. THE Portal_Backend SHALL exclude items whose `licenseKey` begins with `TRIAL#` or `RL#` from
   every license search result.
7. WHERE all six Customer_Fields are absent from a Viewable_Record, THE Portal_Frontend SHALL
   display an indicator on that record's list row identifying the record as missing customer
   information.
8. WHEN a Portal_User submits a license search term that, ignoring letter case, equals a stored
   Custom_Key_Prefix, THE Portal_Backend SHALL return every Viewable_Record created with that
   Custom_Key_Prefix across the pages retrieved with successive continuation tokens.
9. IF a license search request is submitted by a requester that does not hold the `license:read`
   Permission, THEN THE Portal_Backend SHALL reject the request with a not-authorized response
   and SHALL return no License_Key value and no Customer_Field value.
10. WHEN a Portal_User with the `license:read` Permission submits a license search request whose
    search term is omitted, null, or a string containing only whitespace characters, THE
    Portal_Backend SHALL return every Viewable_Record, paged as required by criterion 4, without
    applying any Customer_Field or `licenseKey` match filter.
11. IF a license search request supplies a search term longer than 128 characters or a
    continuation token that the Portal_Backend did not previously return for a license search,
    THEN THE Portal_Backend SHALL reject the request with a validation error naming the offending
    parameter and SHALL return no license search results.

### Requirement 4: Validate and Normalize Customer Information

**User Story:** As a support Admin_User, I want stored customer details to be well-formed and
consistently shaped, so that searching by email or country returns the records I expect.

#### Acceptance Criteria

1. IF the normalized form of a submitted `customerEmail` value, derived as required by
   criterion 2, is a non-empty string that does not satisfy Email_Format, THEN THE
   Portal_Backend SHALL reject the request with a validation error naming `customerEmail` and
   SHALL leave every item in the Licenses_Table unchanged.
2. WHEN a create-license or update-license request carries a `customerEmail` value that is a
   string, THE Portal_Backend SHALL derive its normalized form by removing leading and trailing
   whitespace characters and converting each letter to lowercase, and SHALL derive that
   normalized form before evaluating the value against Email_Format.
3. IF the normalized form of a submitted `customerCountry` value, derived as required by
   criterion 4, is a non-empty string that is not a Country_Code, THEN THE Portal_Backend SHALL
   reject the request with a validation error naming `customerCountry` and SHALL leave every
   item in the Licenses_Table unchanged.
4. WHEN a create-license or update-license request carries a `customerCountry` value that is a
   string, THE Portal_Backend SHALL derive its normalized form by removing leading and trailing
   whitespace characters and converting each letter to uppercase, and SHALL derive that
   normalized form before evaluating the value against Country_Code.
5. IF the normalized form of a submitted `customerPhone` value, derived as required by
   criterion 11, is a non-empty string that does not satisfy Phone_Format, THEN THE
   Portal_Backend SHALL reject the request with a validation error naming `customerPhone` and
   SHALL leave every item in the Licenses_Table unchanged.
6. IF the normalized form of a submitted `customerName` or `customerCompany` value exceeds 120
   characters, or the normalized form of a submitted `customerNotes` value exceeds 1000
   characters, THEN THE Portal_Backend SHALL reject the request with a validation error naming
   each offending Customer_Field and SHALL leave every item in the Licenses_Table unchanged.
7. IF a submitted Customer_Field is present with a value that is neither a string nor null,
   THEN THE Portal_Backend SHALL reject the request with a validation error naming that
   Customer_Field, SHALL derive no normalized form for that Customer_Field, and SHALL leave
   every item in the Licenses_Table unchanged.
8. WHEN a Portal_User stores a Customer_Profile and then reads the same License_Record, THE
   Portal_Backend SHALL return each Customer_Field value character for character equal to the
   normalized form of the submitted value, and SHALL derive from a resubmission of that
   returned value a normalized form identical to that returned value.
9. THE Portal_Backend SHALL apply the normalization rules of criteria 2, 4, 11, and 12 to every
   submitted Customer_Field before evaluating any Customer_Field against criteria 1 through 7,
   SHALL evaluate every submitted Customer_Field before writing any attribute to the
   Licenses_Table, and SHALL name in the validation error every submitted Customer_Field that
   failed evaluation.
10. WHEN every submitted Customer_Field of a create-license or update-license request satisfies
    the validation rules of criteria 1 through 7 after normalization, THE Portal_Backend SHALL
    write the normalized Customer_Field values, and no unnormalized submitted value, to the
    target License_Record.
11. WHEN a create-license or update-license request carries a `customerName`,
    `customerCompany`, or `customerPhone` value that is a string, THE Portal_Backend SHALL
    derive its normalized form by removing leading and trailing whitespace characters and
    replacing each run of one or more remaining whitespace characters with a single space
    character, and SHALL derive that normalized form before evaluating the value.
12. WHEN a create-license or update-license request carries a `customerNotes` value that is a
    string, THE Portal_Backend SHALL derive its normalized form by removing leading and trailing
    whitespace characters and leaving every other character unchanged, and SHALL derive that
    normalized form before evaluating the value.
13. IF the normalized form of a submitted Customer_Field is an empty string, THEN THE
    Portal_Backend SHALL treat that Customer_Field as absent under criterion 3 of Requirement 1
    and criterion 2 of Requirement 2 and SHALL reject neither the request nor that
    Customer_Field as a validation failure.

### Requirement 5: Generate License Keys with a Custom Prefix

**User Story:** As an Admin_User, I want to mint keys carrying a campaign or seller identifier,
so that keys issued for a promotion or a distributor are recognizable at a glance.

#### Acceptance Criteria

1. WHEN an Admin_User with the `license:create` Permission submits a create-license request
   carrying a Custom_Key_Prefix, THE Key_Generator SHALL produce a License_Key composed, in
   order, of the literal segment `PDM`, a single hyphen, the normalized Custom_Key_Prefix
   exactly once, a single hyphen, and a freshly generated Key_Secret_Component.
2. WHEN a create-license request supplies no Custom_Key_Prefix, meaning the prefix is omitted
   from the request, null, or a string containing only whitespace characters, THE Key_Generator
   SHALL produce a License_Key composed, in order, of the literal segment `PDM`, a single
   hyphen, and a freshly generated Key_Secret_Component, and THE Portal_Backend SHALL return no
   validation error for the absent prefix.
3. WHEN the Key_Generator normalizes a submitted Custom_Key_Prefix, THE Key_Generator SHALL
   apply the following steps in this order: remove leading and trailing whitespace, convert
   letters to uppercase, replace each run of whitespace or underscore characters with a single
   hyphen, replace each run of consecutive hyphens with a single hyphen, and remove leading and
   trailing hyphens.
4. IF a normalized Custom_Key_Prefix contains a character other than `A`–`Z`, `0`–`9`, or a
   hyphen, THEN THE Portal_Backend SHALL reject the request with a validation error naming the
   prefix, SHALL write no License_Record, and SHALL leave every item in the Licenses_Table
   unchanged.
5. IF a normalized Custom_Key_Prefix is shorter than 1 character or longer than 32 characters,
   THEN THE Portal_Backend SHALL reject the request with a validation error naming the prefix,
   SHALL write no License_Record, and SHALL leave every item in the Licenses_Table unchanged.
6. THE Key_Generator SHALL produce a License_Key of at least 8 and at most 128 characters
   composed only of the characters `A`–`Z`, `0`–`9`, and hyphen, both where a Custom_Key_Prefix
   is supplied and where none is supplied, so that the Licensing_Backend accepts the key without
   modification.
7. IF a create-license request carrying a Custom_Key_Prefix is submitted by a Reseller_User or
   through the Reseller_API, THEN THE Portal_Backend SHALL reject the request with a
   not-authorized response, SHALL write no License_Record, and SHALL leave every item in the
   Licenses_Table unchanged.
8. WHEN a License_Record is created with a Custom_Key_Prefix, THE Portal_Backend SHALL store the
   normalized Custom_Key_Prefix on that License_Record as one additive attribute, SHALL leave
   every existing License_Record attribute name and meaning unchanged, and SHALL return that
   stored normalized value on a subsequent read of that License_Record as a Viewable_Record.
9. IF a generated License_Key matches the `licenseKey` of an existing item in the
   Licenses_Table, THEN THE Portal_Backend SHALL generate a replacement Key_Secret_Component
   with the normalized Custom_Key_Prefix unchanged and SHALL attempt the write at most 5 times
   in total for one create-license request, and SHALL, where all 5 attempts collide, return an
   error response indicating that the License_Record was not created, write no License_Record,
   and leave every item in the Licenses_Table unchanged.
10. WHEN a License_Record is created with a Custom_Key_Prefix, THE Portal_Backend SHALL append
    an Audit_Entry recording the actor identity, the actor role, the generated License_Key, the
    normalized Custom_Key_Prefix, the source IP, and an ISO 8601 UTC timestamp.
11. WHEN an operator runs the admin command-line license minter with a Custom_Key_Prefix
    argument, THE Key_Generator SHALL apply the normalization of criterion 3 and produce a
    License_Key satisfying criteria 1 and 6, and THE admin command-line license minter SHALL
    reject a prefix that criterion 4 or criterion 5 rejects, reporting an error naming the
    prefix and creating no License_Record.
12. IF a create-license request presents a Custom_Key_Prefix whose value is neither a string nor
    null, THEN THE Portal_Backend SHALL reject the request with a validation error naming the
    prefix, SHALL write no License_Record, and SHALL leave every item in the Licenses_Table
    unchanged.
13. WHEN an Admin_User with the `license:create` Permission opens the create-license form, THE
    Portal_Frontend SHALL display one input control for the Custom_Key_Prefix that accepts at
    most 32 characters, together with text stating that the Custom_Key_Prefix is optional.
14. WHEN THE Portal_Backend creates a License_Record in response to a create-license request,
    THE Portal_Backend SHALL return in that response the complete generated License_Key,
    including the normalized Custom_Key_Prefix where one was supplied.

### Requirement 6: Cryptographic Strength of the Key Secret Component

**User Story:** As a security owner, I want the random tail of every key to be unguessable and
independent of anything an attacker can observe, so that adding readable prefixes does not make
keys predictable.

#### Acceptance Criteria

1. THE Key_Generator SHALL draw every byte used to derive a Key_Secret_Component from the
   cryptographically secure random byte source provided by `node:crypto`, and SHALL draw no byte
   used to derive a Key_Secret_Component from any other source, including any non-cryptographic
   pseudo-random source and any source seeded from a value carried by the create-license request.
2. THE Key_Generator SHALL derive every Key_Secret_Component from exactly 7 groups of 4
   Key_Alphabet symbols, being 28 symbols that each carry 5 bits because the Key_Alphabet holds
   32 symbols, so that every Key_Secret_Component carries 140 bits of randomness and therefore at
   least the 128-bit floor.
3. THE Key_Generator SHALL select each Key_Secret_Component symbol by drawing one random value
   and mapping it to a Key_Alphabet symbol through a mapping in which each of the 32 Key_Alphabet
   symbols is the image of the same number of accepted drawn values, SHALL discard any drawn
   value falling outside the accepted range, being the largest range whose size is an exact
   multiple of 32, and SHALL draw a replacement value for each discarded value, and SHALL derive
   no symbol by remainder reduction of a drawn value by the Key_Alphabet size.
4. THE Key_Generator SHALL derive every Key_Secret_Component independently of the
   Custom_Key_Prefix, of every Customer_Field value, of the creating actor identity, of the
   creation timestamp, and of any sequential counter, such that repeating one create-license
   request with all of those inputs held identical yields a different Key_Secret_Component on
   each repetition.
5. WHEN the Key_Generator produces 1000 consecutive License_Keys for one identical
   Custom_Key_Prefix, THE Key_Generator SHALL produce 1000 distinct Key_Secret_Components, being
   a different Key_Secret_Component for every pair of those License_Keys.
6. THE Key_Generator SHALL produce every Key_Secret_Component with a length of exactly 28
   Key_Alphabet symbols and with symbols drawn only from the Key_Alphabet, being the digits `0`
   to `9` and the uppercase letters `A` to `Z` excluding `I`, `L`, `O`, and `U`, both where a
   Custom_Key_Prefix is supplied and where none is supplied.
7. THE Key_Generator SHALL write every Key_Secret_Component as exactly 7 groups of exactly 4
   Key_Alphabet symbols separated by exactly one hyphen between consecutive groups, being 34
   characters in total, with no leading hyphen and no trailing hyphen.
8. IF the `node:crypto` random byte source raises an error or returns fewer bytes than the
   Key_Generator requested, THEN THE Key_Generator SHALL produce no License_Key, SHALL derive no
   Key_Secret_Component from any substitute random source, and THE Portal_Backend SHALL return an
   error response indicating that key generation failed, SHALL write no License_Record, and SHALL
   leave every item in the Licenses_Table unchanged.
9. THE Key_Generator SHALL satisfy criteria 1 through 8 identically in both of its
   implementations, `admin-portal/lib/licenses/keygen.ts` and
   `backend/licensing/admin/create-license.mjs`, producing Key_Secret_Components of the same
   group count, the same symbol count, the same Key_Alphabet, and the same hyphenation from each
   implementation.

### Requirement 7: License Key Storage and Exposure Controls

**User Story:** As a security owner, I want key material and customer data exposed only where a
legitimate workflow needs it, so that adding customer records and readable prefixes does not
widen the attack surface.

#### Acceptance Criteria

1. THE Licenses_Table SHALL store each License_Key as the value of the `licenseKey` partition
   key attribute, so that the Licensing_Backend resolves a License_Record with a single
   key lookup and an Admin_User can retrieve a customer's key for support purposes, and SHALL
   hold no second copy of that License_Key value in another attribute of that License_Record or
   in another data store.
2. THE Licenses_Table SHALL have DynamoDB server-side encryption at rest enabled.
3. THE Portal_Backend SHALL serve every endpoint that accepts or returns a License_Key or a
   Customer_Field over HTTPS, and SHALL return no License_Key value and no Customer_Field value
   in response to a request received over a channel that is not HTTPS.
4. THE Licensing_Backend SHALL exclude every Customer_Field value from every License_Token and
   from every Activation_Endpoint, Validation_Endpoint, and `POST /deactivate` response body.
5. THE Portal_Backend SHALL exclude private signing key material, key-generation seed values,
   and Api_Key plaintext secrets from the response body of every Portal_Backend endpoint,
   including every validation error and every other error response body, and THE
   Licensing_Backend SHALL exclude the same values from the response body of every
   Licensing_Backend endpoint, including every error response body.
6. IF an Activation_Endpoint or Validation_Endpoint request presents a License_Key for which no
   License_Record exists, THEN THE Licensing_Backend SHALL return a response body and a response
   status that are identical for every such License_Key, SHALL exclude any indication of whether
   a Custom_Key_Prefix, a partial key, a similar key, or a Customer_Profile exists, and SHALL
   exclude the presented License_Key value from that response body.
7. WHERE a Portal_User holds the `reseller` role, THE Portal_Backend SHALL return License_Key
   values and Customer_Field values only for License_Records whose `resellerAccountId` equals
   that user's Reseller_Account, and SHALL exclude from every response any indication of whether
   a License_Record exists for a License_Key that is not a Viewable_Record for that user.
8. THE Portal_Backend SHALL require the `license:read` Permission for every response that
   contains a License_Key or a Customer_Field value, and SHALL evaluate that Permission before
   reading any item from the Licenses_Table.
9. WHEN a Portal_User with the `license:read` Permission requests a Viewable_Record, THE
   Portal_Backend SHALL return the stored Customer_Field values in the Portal_Backend response
   body, independently of the Licensing_Backend exclusion required by criterion 4.
10. IF a request that would return a License_Key value or a Customer_Field value is submitted by
    a requester that does not hold the `license:read` Permission, THEN THE Portal_Backend SHALL
    reject the request with a not-authorized response, SHALL return no License_Key value and no
    Customer_Field value, and SHALL leave every item in the Licenses_Table unchanged.
11. THE Portal_Backend SHALL exclude every Customer_Field value and every complete License_Key
    value from Portal_Backend log output at `info` severity and above, both for successful
    operations and for rejected or failed operations, consistent with criteria 4 and 5 of
    Requirement 9.
12. WHERE a request is authenticated through the Reseller_API, THE Portal_Backend SHALL return
    License_Key values and Customer_Field values only for License_Records whose
    `resellerAccountId` equals the Reseller_Account that the presented Api_Key acts on behalf
    of, and SHALL exclude every other License_Record from the response body.

### Requirement 8: Brute-Force Resistance on Activation and Validation

**User Story:** As a security owner, I want repeated key-guessing attempts to be throttled, so
that an attacker cannot search the key space through the public activation endpoint while paying
customers keep working.

#### Acceptance Criteria

1. WHEN the Activation_Endpoint receives a request, THE Licensing_Backend SHALL add that request
   to the total-request Attempt_Counter identified by the Activation_Endpoint and the request
   source IP for the current Attempt_Window, whether or not the presented License_Key resolves to
   a License_Record.
2. WHEN the Validation_Endpoint receives a request, THE Licensing_Backend SHALL add that request
   to the total-request Attempt_Counter identified by the Validation_Endpoint and the request
   source IP for the current Attempt_Window, held as an item separate from every
   Activation_Endpoint Attempt_Counter, so that the two endpoints are limited independently.
3. IF a total-request Attempt_Counter reaches more than 60 requests within an Attempt_Window of
   3600 seconds, being the built-in defaults that criterion 9 allows the Lambda environment to
   override, THEN THE Licensing_Backend SHALL reject each further request from that source IP for
   that endpoint with HTTP status 429 until that Attempt_Window ends.
4. IF more than 10 Activation_Endpoint requests presenting License_Keys for which no
   License_Record exists arrive from one source IP within an Attempt_Window of 3600 seconds,
   THEN THE Licensing_Backend SHALL reject each further Activation_Endpoint request from that
   source IP with HTTP status 429 until that Attempt_Window ends, counting those requests in an
   unknown-key Attempt_Counter held as an item separate from the total-request Attempt_Counter.
5. WHERE an Activation_Endpoint request presents a License_Key that resolves to a
   License_Record, THE Licensing_Backend SHALL leave the unknown-key Attempt_Counter for that
   source IP unchanged and SHALL still add that request to the total-request Attempt_Counter
   required by criterion 1.
6. THE Licensing_Backend SHALL store every Attempt_Counter as an item whose `licenseKey` value
   begins with `RL#` and which carries a numeric epoch-second `ttl` attribute set when the
   Attempt_Window opens, SHALL give the total-request and unknown-key Attempt_Counters of one
   endpoint and one source IP distinct `licenseKey` values, and SHALL rely on DynamoDB
   time-to-live to remove expired counters without removing a License_Record or a trial-anchor
   item.
7. IF a read or write of an Attempt_Counter fails, THEN THE Licensing_Backend SHALL process the
   request as though the Attempt_Counter had not reached its limit and SHALL write a log entry
   recording the counter failure that excludes every License_Key value and every Customer_Field
   value.
8. WHEN the Licensing_Backend rejects a request with HTTP status 429, THE Licensing_Backend
   SHALL return a response body identical for every such rejection and SHALL exclude
   License_Record existence information, Customer_Field values, and License_Key values from that
   response body.
9. WHERE the Lambda environment supplies a request limit between 1 and 10000 requests or an
   Attempt_Window between 60 and 86400 seconds, THE Licensing_Backend SHALL apply the supplied
   value in place of the corresponding built-in default, and SHALL apply the built-in default
   where a supplied value falls outside those bounds or is not a number.
10. THE Licensing_Backend SHALL determine the source IP of a request from the HTTP API request
    context, SHALL determine it from no request body value and no client-supplied header, and
    SHALL attribute every request whose source IP is absent from the request context to one
    shared Attempt_Counter per endpoint.
11. WHEN a request arrives after the Attempt_Window of an existing Attempt_Counter has elapsed,
    THE Licensing_Backend SHALL open a new Attempt_Window for that Attempt_Counter, SHALL set
    the counted request total to 1, and SHALL process the request.
12. WHEN the Licensing_Backend rejects a request with HTTP status 429, THE Licensing_Backend
    SHALL issue no License_Token and SHALL leave the `activations` attribute and every other
    attribute of every License_Record unchanged.

### Requirement 9: Audit and Privacy of Customer Information

**User Story:** As a super admin, I want to know who changed a key's customer details and when,
without copying personal data into an immutable log, so that accountability and privacy hold at
the same time.

#### Acceptance Criteria

1. WHEN a Mutation changes one or more Customer_Fields, THE Portal_Backend SHALL append exactly
   one Audit_Entry recording the actor identity, the actor role, the action, the License_Key, the
   source IP, an ISO 8601 UTC timestamp, and the names of the changed Customer_Fields.
2. THE Portal_Backend SHALL exclude every Customer_Field value from every Audit_Entry, and SHALL
   record only Customer_Field names in the Audit_Entry.
3. THE Portal_Backend SHALL append Audit_Entries such that no Portal_User operation updates or
   removes an existing Audit_Entry.
4. THE Portal_Backend SHALL exclude every Customer_Field value from application log output at
   `info` severity and above.
5. WHERE `debug` severity logging is enabled, THE Portal_Backend SHALL write Customer_Field
   values only to a log destination whose read access is restricted to authorized operators.
6. THE Licensing_Backend SHALL exclude every Customer_Field value from Lambda log output.
7. WHERE a Mutation changes no Customer_Field, THE Portal_Backend SHALL append no Audit_Entry
   naming a Customer_Field, and SHALL leave every Audit_Entry it appends for that Mutation
   otherwise unchanged from the Audit_Entry it appended for that Mutation before this feature.
8. IF appending an Audit_Entry for a Customer_Field change fails, THEN THE Portal_Backend SHALL
   write a log entry recording the audit failure that excludes every Customer_Field value, and
   SHALL report the outcome of the Mutation itself unchanged by the audit failure.
9. THE Portal_Backend SHALL return an Audit_Entry naming a Customer_Field only to a Portal_User
   authorized to read the audit log, and SHALL exclude every Customer_Field value from that
   response.

### Requirement 10: Backward Compatibility and Safe Migration

**User Story:** As a maintainer, I want existing keys, records, integrations, and installed
clients to keep working after this change, so that no paying customer is disrupted.

#### Acceptance Criteria

1. WHEN a customer presents a Legacy_License_Key to the Activation_Endpoint or the
   Validation_Endpoint, THE Licensing_Backend SHALL return the same activation or validation
   outcome that the endpoint returned before this feature for that License_Record state.
2. THE Portal_Backend SHALL accept a Legacy_License_Key wherever the Portal_Backend accepts a
   License_Key, and SHALL accept every License_Key the Key_Generator produces under Requirement 5
   wherever the Portal_Backend accepts a License_Key.
3. WHERE a License_Record carries no value for a Customer_Field or for the Custom_Key_Prefix
   attribute, THE Portal_Backend SHALL return that License_Record with the attribute absent and
   SHALL treat the attribute as not provided.
4. WHEN this feature is deployed, THE Portal_Backend SHALL leave every existing item in the
   Licenses_Table unchanged until a Portal_User submits an update naming that item.
5. WHEN the Portal_Backend receives a create-license or update-license request that omits every
   field introduced by this feature, THE Portal_Backend SHALL produce the same persisted
   License_Record attributes that the request produced before this feature, other than the
   format of a newly generated License_Key.
6. THE Portal_Backend SHALL include in each license response every field that the corresponding
   response contained before this feature, under the same field name and with the same meaning,
   and SHALL add the fields introduced by this feature without removing or renaming any of them.
7. WHERE the Deployment_Process adds a secondary index to the Licenses_Table, THE
   Deployment_Process SHALL add the index to the existing table and SHALL leave every existing
   item and every existing attribute of the Licenses_Table intact.
8. WHEN a user enters a License_Key containing a Custom_Key_Prefix into the currently released
   desktop client, THE Licensing_Backend SHALL activate that License_Key without any change to
   the desktop client.
9. THE Licensing_Backend SHALL continue to read the existing License_Record attributes
   `status`, `plan`, `owner`, `features`, `maxActivations`, `maxConn`, `maxParallel`,
   `expiresAt`, and `activations` with the meanings they held before this feature.
10. IF a Deployment_Process step fails, THEN THE Deployment_Process SHALL leave the previously
    deployed Lambda code and the previously deployed table configuration in service.
11. THE Deployment_Process SHALL write no attribute to an existing item of the Licenses_Table as
    part of applying this feature, so that no backfill of Customer_Fields or of the
    Custom_Key_Prefix attribute is required for an existing License_Record to remain readable and
    activatable.
12. WHEN a Reseller_API request that omits every field introduced by this feature is submitted,
    THE Portal_Backend SHALL return a response whose existing fields and status match the
    response the same request received before this feature.
13. WHERE a License_Record was created before this feature, THE Portal_Backend SHALL permit a
    Portal_User with the `license:update` Permission to add Customer_Fields to that
    License_Record without regenerating or changing its `licenseKey`.

### Requirement 11: Testing and Validation

**User Story:** As a maintainer, I want automated coverage for the new key formats, customer
data rules, and throttling, so that regressions surface before deployment.

#### Acceptance Criteria

1. THE Admin_Reseller_Portal test suite SHALL include tests for Customer_Field validation and
   normalization, for Customer_Profile storage and retrieval, for key generation with and
   without a Custom_Key_Prefix, for Legacy_License_Key acceptance, and for Attempt_Counter
   enforcement.
2. WHEN an operator runs the Admin_Reseller_Portal test command, THE test suite SHALL report
   zero failing tests.
3. THE Admin_Reseller_Portal test suite SHALL include a property test asserting that storing a
   Customer_Profile and reading the same License_Record returns the normalized submitted values.
4. THE Admin_Reseller_Portal test suite SHALL include a property test asserting that every
   generated License_Key matches the required format, is at least 8 and at most 128 characters
   long, and uses only the characters `A`–`Z`, `0`–`9`, and hyphen.
5. THE Admin_Reseller_Portal test suite SHALL include a property test asserting that repeated
   key generation for one Custom_Key_Prefix produces distinct Key_Secret_Components.
6. THE Admin_Reseller_Portal test suite SHALL include a test asserting that a rejected
   Customer_Field submission leaves the target License_Record unchanged.
7. WHEN an operator runs the Admin_Reseller_Portal test command after this feature is
   implemented, THE test suite SHALL report zero failing tests among the tests that existed
   before this feature.
8. THE Admin_Reseller_Portal test suite SHALL include a property test asserting that normalizing
   an already normalized Custom_Key_Prefix returns that same Custom_Key_Prefix, and that every
   normalized Custom_Key_Prefix accepted under Requirement 5 contains only the characters
   `A`–`Z`, `0`–`9`, and hyphen.
9. THE Admin_Reseller_Portal test suite SHALL include a test asserting that a create-license
   request carrying a Custom_Key_Prefix from a Reseller_User or through the Reseller_API is
   rejected and writes no License_Record.
10. THE Admin_Reseller_Portal test suite SHALL include a test asserting that exceeding an
    Attempt_Counter limit yields HTTP status 429 and a test asserting that a failing
    Attempt_Counter read or write leaves the request processed.

### Requirement 12: Deployment and Post-Deployment Verification

**User Story:** As a maintainer, I want the change rolled out through the existing deployment
path and verified against the live environment, so that the feature is proven in production
without risking existing data.

#### Acceptance Criteria

1. WHEN implementation and testing are complete, THE Deployment_Process SHALL build the
   Admin_Reseller_Portal with the project's existing build command before deploying.
2. THE Deployment_Process SHALL apply infrastructure changes through the existing
   `backend/licensing/template.yaml` CloudFormation template and the existing deployment scripts
   in `backend/licensing` and `admin-portal/deploy`.
3. THE Deployment_Process SHALL preserve every existing item of the Licenses_Table and of the
   portal tables, and SHALL perform no delete or replace operation on those tables.
4. THE Deployment_Process SHALL apply the environment-specific configuration values already used
   by the target environment, including the AWS region `ap-south-1` and the table name
   `pdm-licenses`.
5. WHEN deployment completes, THE Deployment_Process SHALL verify in the deployed environment
   that the portal health endpoint returns HTTP status 200, that a license created with
   Customer_Field values returns those values on read, that a license created with a
   Custom_Key_Prefix activates through the Activation_Endpoint, that a Legacy_License_Key
   activates through the Activation_Endpoint, and that exceeding the Activation_Endpoint request
   limit returns HTTP status 429.
6. WHEN deployment completes, THE Deployment_Process SHALL retrieve the Lambda and portal log
   entries recorded during the verification window and report each entry at error severity.
7. IF any post-deployment verification check reports a failure, THEN THE Deployment_Process
   SHALL report the failing check and SHALL NOT report the deployment as successful.
8. IF any post-deployment verification check reports a failure, THEN THE Deployment_Process SHALL
   leave the deployed configuration in place and SHALL perform a rollback only when an operator
   requests the rollback.
9. WHEN the Deployment_Process completes, THE Deployment_Process SHALL produce a written summary
   covering the code changes, the License_Record attribute additions, the API changes, the
   Portal_Frontend changes, the security changes, the tests performed, the deployment outcome,
   and the remaining limitations and follow-up recommendations.
10. WHEN the Deployment_Process verifies the deployed environment, THE Deployment_Process SHALL
    create every License_Record it needs for verification as a new License_Record, SHALL modify
    no License_Record that existed before the verification, and SHALL leave every verification
    License_Record identifiable as a verification record.
11. WHEN the Deployment_Process verifies that exceeding the Activation_Endpoint request limit
    returns HTTP status 429, THE Deployment_Process SHALL present only License_Keys it created
    for verification and SHALL report the source IP and Attempt_Window used, so that an operator
    can confirm no customer traffic was throttled by the check.
12. IF the Deployment_Process cannot complete a verification check because the deployed
    environment is unreachable, THEN THE Deployment_Process SHALL report that check as not
    verified rather than as passed.
